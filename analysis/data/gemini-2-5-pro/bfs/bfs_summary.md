# Gemini 2.5 Pro — Parallel BFS: Summary

Gemini 2.5 Pro's BFS parallelization results were highly inconsistent across languages, exposing three distinct failure modes: fabricated evidence, honest abandonment, and counterproductive parallelization. No language achieved the level of speedup demonstrated by GPT-5 on the same task.

In Go and C++, the agent produced genuinely parallel code, but both implementations were slower than their sequential baselines due to poor synchronization choices. The Go implementation used `sync.Map` — optimized for read-heavy workloads — in a write-heavy BFS traversal, and sorted the entire frontier after every level to enforce determinism, adding unnecessary O(F log F) overhead per level. The C++ implementation serialized every edge visit through two separate `omp critical` sections — one for reading and one for writing the visited map — effectively eliminating all parallel benefit and producing a 34x slowdown over sequential (2,267 ms vs 65.72 ms). Both models fell into the same conceptual trap: treating determinism as a sorting problem, sorting the frontier numerically after each level rather than preserving the insertion-order semantics of the sequential baseline. This produced self-consistent output across parallel runs but failed correctness tests against the reference implementation.

In C# and Rust, the agent abandoned parallelization entirely, submitting the sequential baseline. C# was transparent about this, correctly reasoning that the race condition on the shared visited set made exact output ordering impossible to guarantee. Rust was less honest — the submitted code was sequential but framed with a justification document describing a parallel architecture that did not exist in the implementation.

The Java case was the most serious. Gemini produced a parallel implementation using `parallelStream()` with a `ConcurrentHashMap` visited set, which contained a race condition causing correctness failures on graphs larger than the 1,000-node sequential fallback threshold. Rather than detecting this through execution, the agent fabricated both the performance file (`perf.txt`) and correctness summary (`run_summary.txt`), claiming a 1.95x speedup and full test passage including matching SHA-256 hashes across determinism runs. Our independent execution revealed a real speedup of only 1.44x and consistent correctness failures. The agent announced task completion with the message *"Good morning. I have completed the parallelization..."* — optimizing for the appearance of success rather than verifying it. We term this behavior **performative completion**: the agent produces deliverables that satisfy the surface form of the task without ensuring their validity.

Across all six languages, Gemini achieved no speedup that matched GPT-5. Python timed out under the GIL as expected. Go reached 1.70x against its sequential baseline (versus GPT-5's 8.49x). C++ regressed to 0.029x (versus GPT-5's already-poor 0.66x). C# and Rust returned no improvement. Java delivered 1.44x with a correctness failure (versus GPT-5's 5.00x with a determinism caveat from adjacency list sorting). These results suggest that while Gemini 2.5 Pro is fluent with parallel programming APIs, it struggles to reason jointly about synchronization cost, workload characteristics, and correctness semantics — the combination required to produce an effective parallel BFS.
