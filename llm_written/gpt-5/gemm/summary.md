# GPT-5 Parallel GEMM: A Cross-Language Analysis

## Thesis-Ready Summary

GPT-5 produced structurally consistent parallel GEMM implementations across all six languages. Every implementation preserves numerical determinism through disjoint row-writes and fixed K-summation order, and all include a small-input fallback to avoid parallel overhead on trivial problem sizes. Five of the six parallelize the M-dimension of the tiled loop nest; Java is the exception, distributing work over (M, N) tile pairs with the K-loop running sequentially inside each task.

The performance spread across languages is substantial, ranging from a 7.4x speedup in Go to a 13% regression in C++. This variance is driven primarily by the cost of the chosen concurrency primitive rather than by algorithmic differences. Go's channel-based worker pool leverages goroutine scheduling at roughly 50 ns per task dispatch, enabling near-ideal scaling. Rust's scoped threads achieve a 4.5x speedup through a clone-local-merge pattern that avoids shared mutable state entirely, though the row-cloning overhead limits parallel efficiency to 56%. C# benefits from the TPL's adaptive work-stealing scheduler for a 3.3x gain. Python, despite the cost of pickle serialization across process boundaries, still achieves a 3x speedup, limited mainly by a hard cap of four worker processes. Java shows only marginal improvement at the benchmark size due to JVM task-management overhead, though it scales better at smaller matrix dimensions. The C++ implementation is the sole regression: GPT-5 placed the OpenMP directive on the innermost M-loop inside the (N, K) tile loops, creating 256 fork-join barriers per multiply. The accumulated synchronization cost exceeds the computational benefit, resulting in a net slowdown.

These results highlight a consistent gap in GPT-5's parallel code generation: while the model reliably selects safe parallelization patterns (disjoint writes, bounded worker counts, deterministic accumulation), it does not reason about where in the loop nest to introduce parallelism to minimize synchronization frequency. The choice of concurrency primitive and its placement, rather than the parallelization strategy itself, emerge as the dominant factors determining performance.

## Detailed Reference

### 1. Scope

This chapter examines the parallel General Matrix Multiply (GEMM) implementations generated by GPT-5 across six programming languages. Each implementation was tasked with parallelizing a common blocked GEMM kernel (`C := αAB + βC`) using language-idiomatic concurrency primitives. All measurements use a fixed **1024 x 1024 x 1024** matrix with **20 iterations and 5 repeats**.

## 3. Shared Algorithmic Baseline

GPT-5 produced a structurally consistent sequential kernel across all six languages:

- **Tiling:** 3-level blocking with MB = NB = KB = 64
- **Loop order:** N-blocks → K-blocks → M-blocks (outer to inner)
- **B transpose:** Performed once before the tiled loops for cache-friendly dot products
- **Kernel:** `partialMatmul` accumulates partial products into C with α-scaling

This uniformity isolates the parallelization strategy as the primary variable across languages.

## 4. Parallelization Strategies

### 4.1 What GPT-5 Chose for Each Language

| Language | Parallel Dimension | Primitive | Worker Bound | Small-Input Threshold |
|----------|-------------------|-----------|-------------|----------------------|
| C++ | M-tiles (inner loop) | `#pragma omp parallel for` | `omp_get_max_threads()` | m\*n\*k ≤ 200,000 |
| Go | M-tiles (inner loop) | Channel-based worker pool | `GOMAXPROCS` | m\*n ≤ 10 |
| Java | (M, N) tile pairs | `ExecutorService` + `invokeAll` | `availableProcessors()` | m\*n\*k ≤ 500,000 |
| Rust | M-row bands | `thread::scope` + `spawn` | `available_parallelism` | m\*n\*k ≤ 131,072 |
| C# | M-tiles (inner loop) | `Parallel.For` | `ProcessorCount` | m\*n\*k ≤ 1,000,000 |
| Python | M-tiles (inner loop) | `ProcessPoolExecutor` | min(cpu\_count, 4) | total\_elems ≤ 1,024 |

All implementations share two design invariants:

1. **Disjoint writes.** Each worker writes to exclusive rows (or row-column tiles) of C, eliminating write conflicts without locks.
2. **Deterministic accumulation.** The K-dimension summation order is preserved within each worker, maintaining bit-exact reproducibility with the sequential baseline.

### 4.2 Structural Differences

**Java** is the only implementation that parallelizes over two dimensions (M, N), creating one task per (M, N) tile pair with the K-loop running sequentially inside each task. This creates 256 tasks at 1024^3, each performing 8.4M FLOPs.

**Rust** uses a clone-local-merge pattern: each worker clones its assigned rows of C, computes locally, and returns results that are merged in sorted row order. This avoids shared mutable state entirely at the cost of additional memory traffic (~8 MB per worker for cloning).

**Go** keeps its worker pool alive across M-tile iterations within each (N, K) pair, effectively amortizing goroutine creation. Workers consume jobs from a channel rather than being spawned per tile.

**C++, C#, and Python** all parallelize the innermost M-loop within the nested (N, K) loops, creating a synchronization barrier at every (N, K) iteration (256 barriers for 1024^3).

## 5. Analysis: Why the Speedups Differ

### 5.1 Concurrency Primitive Overhead

The dominant factor separating the six implementations is the cost of creating, scheduling, and synchronizing parallel work units.

| Primitive | Approx. per-task overhead | Barrier count (1024^3) | Cumulative overhead |
|-----------|--------------------------|----------------------|-------------------|
| Goroutine + channel send | ~50 ns | 256 | ~13 μs |
| `thread::scope` spawn | ~1 μs | 1 (per GEMM call) | ~8 μs |
| `Parallel.For` iteration | ~100 ns | 256 | ~26 μs |
| `ProcessPoolExecutor` submit | ~0.1-1 ms (pickle) | 256 | ~25-250 ms |
| `ExecutorService` + lambda | ~150 ns | 1 (invokeAll) | ~38 μs |
| OpenMP fork/join | ~1-10 μs | 256 | ~0.26-2.56 ms |

Go achieves the best speedup because goroutines and channels are the lightest concurrency primitive in this set. The M:N scheduler maps goroutines onto OS threads without per-task allocation overhead.

C++ OpenMP suffers because the `#pragma omp parallel for` directive is placed inside the (N, K) loop, causing **256 fork-join barriers**. Each barrier incurs thread synchronization overhead that, in aggregate, exceeds the computational benefit of parallelism.

### 5.2 Data Movement Costs

| Language | Data sharing mechanism | Copy overhead per task |
|----------|----------------------|----------------------|
| Go | Slice views (zero-copy headers) | ~0 |
| Rust | Shared borrow for B; clone rows for C | ~8 MB total |
| C# | `Array.Copy` for packing | Moderate |
| C++ | Stack allocation per `packMatrix` call | Allocation contention |
| Java | Pre-packed 4D array, lambda captures | Object allocation pressure |
| Python | Pickle serialization (full copy) | ~24 KB per task, ~100 MB total |

Go's slice semantics provide zero-copy submatrix access (`out[i] = matrix[b0+i][a0:a1]`), eliminating allocation from the hot path entirely. Python sits at the opposite extreme, serializing every input and output through pickle for inter-process transfer.

### 5.3 Granularity and Synchronization

The number of synchronization points relative to the amount of work between them determines parallel efficiency.

For the M-loop parallelization used by C++, C#, and Python, each of the 256 (N, K) iterations exposes only 16 M-tiles for parallel execution. With 8 cores, each core processes ~2 tiles per barrier, yielding:

```
Work per core per barrier = 2 × 524,288 FLOPs ≈ 1M FLOPs
```

At a sustained throughput of ~1-5 GFLOP/s per core (depending on language), this amounts to 0.2-1.0 ms of computation between barriers. When barrier overhead approaches this range (as in C++ OpenMP), parallelism fails to deliver a net benefit.

Java's 2D tiling approach avoids repeated barriers by issuing all 256 tasks in a single `invokeAll`, but the JVM's lambda allocation and task queue management introduce a different class of overhead.

Rust's single-spawn-per-GEMM approach incurs only one synchronization point, but the clone-merge pattern adds a sequential data movement phase.

## 6. Parallel Efficiency

Parallel efficiency is defined as:

```
η = Speedup / P
```

where P is the number of worker threads (assumed 8 for this analysis).

| Language | Speedup | η (8 cores) | Primary limiter |
|----------|---------|-------------|-----------------|
| Go | 7.40x | 92.5% | Near-ideal |
| Rust | 4.50x | 56.3% | Clone-merge overhead |
| C# | 3.26x | 40.8% | Runtime overhead + memory bandwidth |
| Python | 3.04x | 76.0% (4 workers) | IPC serialization, worker cap |
| Java | 1.05x | 13.1% | JVM overhead at large size |
| C++ | 0.87x | N/A | Regression (overhead > benefit) |

> **Note on Python efficiency.** Python caps workers at 4, so η = 3.04/4 = 76%, which is respectable given the serialization overhead. The bottleneck is the hard worker cap and pickle cost, not the parallelization strategy itself.

## 7. Correctness Properties

All six implementations preserve numerical determinism through the same structural guarantee:

1. Each worker writes to a disjoint subset of C (no write conflicts)
2. The K-dimension summation proceeds in fixed left-to-right order within each worker
3. No floating-point reductions occur across thread boundaries

The Rust implementation adds an additional determinism guarantee: results are merged in sorted row order regardless of thread completion order, making the output independent of scheduling decisions.

## 8. Observations

### 8.1 GPT-5 Consistently Chose M-Dimension Parallelism

Five of six implementations parallelize over the M-dimension. This is a reasonable default since M-tiles produce disjoint row stripes in C, eliminating write conflicts without synchronization. However, this choice is not always optimal. In C++, moving the `parallel for` directive to the outer loop (or collapsing loops) would reduce barrier count from 256 to 1, likely converting the regression into a speedup.

### 8.2 Runtime Overhead Dominates Algorithmic Differences

The spread in speedup (0.87x to 7.40x) is driven primarily by language runtime characteristics rather than algorithmic innovation. All implementations use essentially the same blocked algorithm; only the concurrency wrapper differs. This suggests that for LLM-generated parallel code, the model's choice of concurrency primitive and its placement within the loop nest matter more than the parallelization strategy itself.

### 8.3 Small-Input Fallback Thresholds Vary Widely

GPT-5 selected thresholds ranging from 10 (Go) to 1,000,000 (C#). There is no evidence that these values were empirically tuned. An overly aggressive threshold (Go: `m*n ≤ 10`) provides almost no protection against parallel overhead on small inputs, while an overly conservative one may miss parallelization opportunities.

### 8.4 No Implementation Uses Shared Memory

None of the six implementations employ shared-memory techniques (memory-mapped files, `multiprocessing.shared_memory`, POSIX shm). In Python, this is the most impactful missing optimization, as it would eliminate pickle serialization entirely. In Rust, it would remove the need for the clone-merge pattern.

---

## 9. Conclusions

GPT-5 demonstrates competence in generating structurally correct parallel GEMM implementations across diverse language ecosystems. All six implementations preserve numerical determinism and avoid data races. However, the performance outcomes vary dramatically, from a 7.4x speedup in Go to a 13% regression in C++, driven primarily by:

1. **Concurrency primitive cost.** Goroutines (~50 ns) vs. OpenMP barriers (~1-10 μs) vs. Python pickle (~0.1-1 ms) per task.
2. **Synchronization frequency.** Placing parallel constructs inside inner loops (C++, C#, Python) multiplies barrier overhead by the number of outer-loop iterations.
3. **Data transfer mechanism.** Zero-copy (Go slices) vs. full serialization (Python pickle) determines the communication-to-computation ratio.

The model shows a strong preference for M-dimension parallelism with disjoint writes, a pattern that is safe but not always efficient. The key gap is in *placement*: GPT-5 does not reason about where in the loop nest to introduce parallelism to minimize synchronization frequency. This is most visible in the C++ implementation, where moving the OpenMP directive one loop level outward would likely convert a regression into a speedup.

For thesis purposes, these results establish that LLM-generated parallel code can be functionally correct across languages while exhibiting substantial performance variance rooted in concurrency-primitive selection and loop-level placement decisions.
