# GPT-5 Parallel SCC: A Cross-Language Analysis

## Thesis-Ready Summary

GPT-5 produced structurally uniform parallel SCC implementations across all six languages. Every implementation follows the same two-phase pattern: sequential SCC discovery using Tarjan's or Kosaraju's algorithm, followed by embarrassingly parallel per-SCC edge minimization. Within the parallel phase, each SCC is assigned to an independent worker that builds forward and reverse spanning trees to extract essential edges. All six implementations include a small-input fallback to avoid overhead when the number of SCCs is too small to benefit from parallelism.

The performance spread is wide, ranging from a 5.15x speedup in C++ to a catastrophic 125x slowdown in Python. Four of the six implementations achieve meaningful speedups: C++ (5.15x) benefits from OpenMP's low-overhead static scheduling over per-SCC work units, Rust (3.53x) uses Rayon's work-stealing par_iter to distribute SCC processing, Java (3.05x) employs a fixed-size ExecutorService thread pool, and Go (2.08x) uses a goroutine worker pool with channel-based job dispatch. C# achieves only a marginal 1.44x gain despite using Parallel.For, likely because the edge minimization work per SCC is too fine-grained to overcome the runtime's task scheduling overhead. Python suffers a 125x regression because ProcessPoolExecutor pickles the entire graph adjacency structure to each worker process, making the serialization cost orders of magnitude larger than the per-SCC computation.

A recurring inconsistency across all six implementations is the treatment of reverse spanning tree edges. Every implementation builds a reverse spanning tree by traversing the reversed adjacency list, but stores the resulting edges in reverse-graph orientation without flipping them back to original-graph direction. None of the six justification documents acknowledge this directional discrepancy, which affects the semantic meaning of the "essential edges" output. The justification documents also exhibit a pattern of overstating determinism guarantees: they attribute deterministic output to parallel scheduling discipline (fixed splits and merge order) while underemphasizing the critical dependency on stable adjacency list traversal order within the spanning tree construction. The Java justification contains the most significant fabrication, claiming to have replaced a recursive Tarjan SCC algorithm with iterative Kosaraju, when in fact the baseline already used iterative Kosaraju and the SCC discovery code was copied verbatim.

These results demonstrate that GPT-5 reliably identifies the correct decomposition point for SCC parallelism (per-SCC edge minimization is embarrassingly parallel) and selects appropriate language-idiomatic concurrency primitives. However, the model does not reason about the overhead-to-work ratio of its parallelization choices, as evidenced by Python's catastrophic regression and C#'s marginal gain. The model also shows a tendency to fabricate justification narratives around changes it did not actually make, and to provide incomplete reasoning about correctness properties like determinism.

## Detailed Reference

### 1. Scope

This chapter examines the parallel Strongly Connected Components (SCC) edge minimization implementations generated by GPT-5 across six programming languages. The benchmark pipeline has two phases: SCC discovery (finding strongly connected components via Tarjan's or Kosaraju's algorithm) and edge minimization (for each SCC, building forward and reverse spanning trees to identify essential edges). Only the edge minimization phase is parallelized. The benchmark graph uses V=5000 vertices with approximately 20,000 edges. Performance is measured as the total ReduceEdge time (both phases combined).

> **Note on Python.** The 125x slowdown is caused by ProcessPoolExecutor pickling the entire graph adjacency structure to each worker process. The per-SCC computation (spanning tree DFS) is trivially cheap compared to the serialization overhead, making process-based parallelism fundamentally unsuitable for this workload at this scale.

> **Note on self-reported performance.** GPT-5's own perf.txt files report substantially different results from the standardized benchmark. C++ self-reports 0.90x (regression), C# self-reports 0.62x, Java self-reports 1.41x, Rust self-reports 1.12x, and Go self-reports 2.04x. These discrepancies arise from different graph sizes and topologies in the self-tests. Notably, the Rust self-test uses a single-ring graph (one SCC) that triggers the sequential fallback, meaning its "parallel" benchmark never actually exercises the parallel code path.

## 3. Shared Algorithmic Pattern

All six implementations follow the same two-phase architecture:

1. **Sequential SCC discovery:** Tarjan's iterative DFS (C++, Python, Rust, C#, Go) or Kosaraju's iterative two-pass algorithm (Java). This phase is inherently sequential and produces an ordered list of SCCs.
2. **Parallel edge minimization:** For each SCC, an independent worker builds a forward spanning tree (DFS on original adjacency list) and a reverse spanning tree (DFS on reversed adjacency list), then returns the union of tree edges as the essential edge set.

This decomposition is sound: SCC discovery is inherently sequential (Tarjan's DFS maintains global state via a stack and low-link values), while per-SCC edge minimization is embarrassingly parallel with no inter-SCC dependencies.

## 4. Parallelization Strategies

| Language | Primitive | Worker Bound | Small-N Fallback | SCC Algorithm |
|----------|-----------|-------------|-----------------|---------------|
| C++ | `#pragma omp parallel for schedule(static)` | `omp_get_max_threads()` | SCC count <= 3 | Tarjan (iterative) |
| Java | `ExecutorService` fixed thread pool | `availableProcessors()` | V <= 1000 or SCC count <= 1 | Kosaraju (iterative) |
| Python | `ProcessPoolExecutor` with initializer | `os.cpu_count()` | SCC count <= 2 | Tarjan (via baseline) |
| Rust | Rayon `par_iter().map().collect()` | Rayon global pool (CPU count) | V <= 1024 or SCC count <= 2 | Tarjan (iterative) |
| C# | `Parallel.For` with MaxDegreeOfParallelism | `Environment.ProcessorCount` | SCC count <= 1 | Tarjan (iterative) |
| Go | Goroutine worker pool with channels | `runtime.NumCPU()` | SCC count < 4 | Tarjan (iterative) |

All implementations share two design invariants:

1. **Disjoint writes.** Each worker writes to an exclusive output slot (indexed by SCC), eliminating write conflicts without locks.
2. **Deterministic merge.** Results are concatenated in SCC index order, producing identical output regardless of worker completion order.

### Structural Differences

**Java** is the only implementation that changed the SCC discovery algorithm. While the justification claims this was a deliberate switch from recursive Tarjan to iterative Kosaraju, the baseline already used iterative Kosaraju; the findSCCs() method was copied verbatim.

**Go** maintains a persistent worker pool with channel-based job dispatch, amortizing goroutine creation across all SCCs. However, the small-N fallback path calls FindSCCs twice (once to check the threshold, once inside ReduceEdgesSequential), doubling the cost of the sequential phase.

**Python** uses the initializer pattern to transfer the graph to worker processes, but ProcessPoolExecutor still pickles the full adjacency structure per worker, negating the intended efficiency benefit.

**C#** has the most conservative fallback threshold (SCC count <= 1), meaning it only falls back for trivial graphs with zero or one SCC. This is internally contradicted by its own self-reported 0.62x performance at N=2000.

## 5. Analysis: Why the Speedups Differ

### 5.1 Amdahl's Law and Sequential Fraction

The SCC discovery phase (FindSCC) is inherently sequential and constitutes a varying fraction of total runtime:

| Language | FindSCC (ms) | Total Seq (ms) | Sequential Fraction |
|----------|-------------|---------------|-------------------|
| C++ | 5.25 | 66.83 | 7.9% |
| Java | 6.50 | 45.52 | 14.3% |
| Rust | 5.28 | 39.16 | 13.5% |
| C# | 4.98 | 39.90 | 12.5% |
| Go | 9.47 | 161.37 | 5.9% |
| Python | 166.77 | 268.61 | 62.1% |

With 8 cores and perfect parallelization of the remaining fraction, Amdahl's law predicts maximum speedups of 6.4x (C++), 4.5x (Java), 4.6x (Rust), 4.7x (C#), 6.6x (Go), and 1.5x (Python). The actual speedups for C++ (5.15x), Rust (3.53x), Java (3.05x), and Go (2.08x) fall within these bounds, suggesting the implementations are reasonably efficient. C# (1.44x) significantly underperforms its theoretical limit (4.7x), indicating substantial runtime overhead from Parallel.For task scheduling.

### 5.2 Per-SCC Work Granularity

The edge minimization work per SCC depends on SCC size. For a graph with V=5000, if many SCCs are small (singletons or pairs), each worker performs only a trivial DFS, making the overhead of dispatching work to a thread or process proportionally large. This particularly hurts:

- **Python:** Process dispatch overhead (~1-10 ms per task including pickle) vastly exceeds per-SCC DFS cost (~microseconds).
- **C#:** Parallel.For's ThreadPool dispatch overhead is non-trivial relative to small-SCC work, explaining the gap between theoretical and actual speedup.

### 5.3 Concurrency Primitive Overhead

| Primitive | Per-task overhead | Impact on SCC workload |
|-----------|-----------------|----------------------|
| OpenMP static schedule | ~1 us (one-time partition) | Minimal: single fork-join |
| Rayon par_iter | ~100 ns (work-stealing) | Low: adaptive granularity |
| ExecutorService submit | ~150 ns (lambda + queue) | Low: one task per SCC |
| Goroutine + channel | ~50 ns | Low: lightweight dispatch |
| Parallel.For | ~100 ns per iteration | Moderate: fixed partitioning overhead |
| ProcessPoolExecutor | ~1-10 ms (pickle + IPC) | Catastrophic: dominates computation |

## 6. Justification-vs-Code Inconsistencies

### 6.1 Cross-Cutting Issues (All Six Languages)

**Reverse tree edge direction (HIGH).** Every implementation builds a reverse spanning tree by traversing the reversed adjacency list, but stores edges in reverse-graph orientation (i.e., if original edge is u->v, the reverse tree stores v->u). No justification acknowledges this. Whether this is a correctness bug depends on downstream expectations for the essential edge set.

**Incomplete determinism reasoning (MEDIUM-HIGH).** All justifications attribute determinism to parallel scheduling discipline (fixed task-to-worker assignment and merge order). None acknowledge the more fundamental prerequisite: that BuildSpanningTree produces a deterministic spanning tree because adjacency list iteration order is stable. Several implementations use HashSets or unordered_sets internally, where iteration order is non-deterministic; determinism is preserved only because these containers are queried for membership, not iterated for output, and results are sorted afterward.

### 6.2 Language-Specific Issues

**Java -- Fabricated algorithm change (HIGH).** The justification claims the baseline used "recursive Tarjan's DFS" and was "replaced with iterative Kosaraju." In reality, the baseline (`GraphSeq.java`) already used iterative Kosaraju, and `findSCCs()` in AlgoParallel.java is a verbatim copy. The entire "what changed and why" narrative is fabricated.

**Rust -- Missing fallback threshold (HIGH).** The justification claims a three-part fallback: "V <= 1024 or E <= 5000 or SCCs <= 2." The code only checks V <= 1024 and SCCs <= 2; the edge-count threshold is absent despite having an `edge_count()` helper method available.

**Rust -- Dead parallel code (HIGH).** All test graphs are single-ring topologies producing exactly one SCC, which triggers the sequential fallback. The parallel code path (Rayon par_iter) is never exercised by any test or benchmark.

**Python -- Catastrophic performance unacknowledged (CRITICAL).** The justification predicts ">=1.3x speedup for large inputs." The actual measurement is a 125x slowdown. The perf.txt file contains only a placeholder instruction, not actual data.

**C++ -- Determinism depends on sort (HIGH).** BuildSpanningTree uses `unordered_set<pair<int,int>>` for spanning tree edges, whose iteration order is non-deterministic. The subsequent sort_edges() call neutralizes this, but the justification does not credit the sort as the critical determinism mechanism.

**C# -- Parallel.For scheduling mischaracterized (MEDIUM).** The justification claims "each worker takes specific indexes assigned by Parallel.For," implying static assignment. Parallel.For actually uses dynamic partitioning with work-stealing. The behavioral effect (each index processed exactly once) is the same, but the mechanism description is factually wrong.

**Go -- Double FindSCCs in fallback (MEDIUM).** The "fast path" sequential fallback calls FindSCCs once to check the threshold, then calls ReduceEdgesSequential which calls FindSCCs again internally, performing the most expensive sequential phase twice.

## 7. Correctness Properties

All six implementations preserve output determinism through two mechanisms:

1. **Index-ordered merge:** Results are collected by SCC index, not by worker completion order.
2. **Edge sorting:** Most implementations sort edges within each SCC (by source then destination), providing a canonical order regardless of DFS traversal variations.

## 8. Observations

### 8.1 GPT-5 Correctly Identifies the Parallelization Decomposition

The SCC problem has a naturally sequential component (Tarjan/Kosaraju DFS) and a naturally parallel component (per-SCC edge minimization). GPT-5 correctly identifies this decomposition in all six languages, never attempting to parallelize SCC discovery itself. This represents sound algorithmic reasoning about the problem structure.

### 8.2 Overhead-to-Work Ratio Is Not Considered

While GPT-5 reliably selects appropriate concurrency primitives for each language, it does not reason about whether the per-task work is large enough to justify the parallelization overhead. Python's ProcessPoolExecutor is the most extreme example (pickle serialization dwarfs per-SCC DFS), but C#'s marginal 1.44x also suggests insufficient consideration of task granularity.

### 8.3 Self-Test Graphs Do Not Exercise Parallel Paths

Several implementations use trivially structured test graphs (single rings, small cliques) that trigger the sequential fallback rather than the parallel code path. The Rust implementation is the most egregious case, where every test and benchmark graph produces a single SCC, meaning the Rayon-based parallel path is effectively dead code that has never been executed.

### 8.4 Justification Quality Varies Widely

The justification documents range from broadly accurate (C++, Go) to containing fabricated narratives (Java). The common weakness is incomplete determinism reasoning and failure to acknowledge the reverse edge direction issue. The Java justification's claim of replacing Tarjan with Kosaraju, when the baseline was already Kosaraju and the code was copied verbatim, represents the most significant integrity concern.

---

## 9. Conclusions

GPT-5 demonstrates consistent ability to identify the correct parallelization decomposition for the SCC problem across all six languages. The embarrassingly parallel per-SCC edge minimization pattern is a sound choice, and the implementations achieve meaningful speedups in four of six languages (1.44x to 5.15x). The two failure cases, Python (125x regression) and to a lesser extent C# (marginal gain), are caused by choosing concurrency primitives whose overhead exceeds the per-task work, not by incorrect parallelization strategy.

The key weaknesses are:

1. **Overhead blindness.** GPT-5 does not evaluate whether per-SCC work justifies the chosen parallelization mechanism, leading to catastrophic regression in Python.
2. **Justification fabrication.** The Java justification invents a narrative about algorithm changes that never occurred, suggesting the model generates plausible-sounding explanations without verifying them against the actual code.
3. **Inadequate testing.** Several self-test suites use graph topologies that never exercise the parallel code path, providing no evidence that the parallel implementation is correct.
4. **Reverse edge direction.** A systematic issue across all six implementations where reverse spanning tree edges are stored in reverse-graph orientation, potentially affecting downstream correctness depending on consumer expectations.

For thesis purposes, these results show that LLM-generated parallel SCC code reliably identifies the correct decomposition point but fails to reason about overhead-to-work ratios, produces justification documents with fabricated or incomplete technical narratives, and generates test suites that do not adequately cover the parallel code paths.
