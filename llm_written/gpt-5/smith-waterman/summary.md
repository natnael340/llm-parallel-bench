# GPT-5 Smith-Waterman Parallel Analysis

GPT-5 was given sequential Smith-Waterman implementations in six languages and tasked with producing correct, deterministic, resource-bounded parallel versions. It chose the same strategy everywhere: anti-diagonal (wavefront) parallelism, where cells on the same anti-diagonal are independent and can be computed concurrently. Only the matrix fill is parallelized; traceback remains sequential. All implementations include a sequential fallback for small inputs. GPT-5's justifications were templated across all six languages---identical ASCII diagrams, glossaries, and structure---suggesting pattern reuse rather than language-specific reasoning.

Correctness was achieved universally. All six implementations pass correctness and determinism tests, producing identical results to the sequential baselines across repeated executions. This is a nontrivial achievement given the constraints of parallel determinism.

Performance splits cleanly by concurrency primitive and synchronization granularity. Python achieved the strongest speedup at 5.05x (sequential 216,645 ms, parallel 42,910 ms), but through NumPy vectorization rather than explicit threading---GPT-5 adaptively pivoted to this after a failed ProcessPoolExecutor attempt. The large speedup is partly because the sequential Python baseline is extremely slow interpreted loops, making NumPy's C-level execution a massive win. Go achieved 2.78x (sequential 3,628 ms, parallel 1,307 ms) using goroutines with a 32x32 tiled wavefront, and C# achieved 2.62x (sequential 3,108 ms, parallel 1,187 ms) using TPL Parallel.For with 128x128 tiles. Both use tile-based blocking that reduces synchronization points from O(n+m) individual diagonals to O(n/T + m/T) tile-diagonals---this amortization proved critical. C++ achieved a modest 1.16x (sequential 1,417 ms, parallel 1,226 ms) using OpenMP, where the already-fast sequential baseline leaves little headroom.

Java and Rust failed catastrophically. Java ran 16.6x slower than sequential (sequential 2,005 ms, parallel 33,302 ms) due to ExecutorService with a CyclicBarrier per anti-diagonal, forcing all threads through an OS-level synchronization point at every one of thousands of diagonals. Rust ran 49x slower (sequential 1,079 ms, parallel 53,111 ms) by spawning scoped OS threads via std::thread::scope for every anti-diagonal---thread creation and destruction thousands of times per matrix fill is ruinously expensive. Rust should have used Rayon's thread pool; Java needed a design without per-diagonal barriers.

The critical finding is that GPT-5's choice of concurrency primitive matters more than its algorithm strategy. The wavefront approach is sound in all cases, but low-cost primitives (goroutines, TPL, OpenMP, NumPy) yield speedup while expensive primitives (raw OS thread spawning, heavyweight barriers) produce catastrophic slowdown. Tiling further differentiates success from failure among the explicitly threaded implementations, emerging as the key architectural decision.
