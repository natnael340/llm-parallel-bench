# Gemini 2.5 Pro Parallel GEMM: A Cross-Language Analysis

## Thesis-Ready Summary

Gemini 2.5 Pro produced parallel GEMM implementations across all six languages with a clear strategic split: three implementations (Go, Python, C++) parallelize over 2D (M, N) tile pairs with the K-loop running sequentially inside each worker, while the remaining three (Java, C#, Rust) parallelize only the M-dimension within sequential (N, K) loops. This architectural decision dominates the performance outcomes. Go achieves the best speedup at 9.5x using semaphore-bounded goroutines, with each goroutine owning a complete (M, N) output block and iterating K internally, producing a single synchronization point. Python achieves a notable 8.5x speedup despite using process-based parallelism, enabled by an initializer pattern that passes matrices to workers at pool creation rather than serializing them per task, and by removing the worker cap that limited GPT-5's Python to 4 processes. C++ uses OpenMP's `collapse(2)` directive to merge the N and M loops into a single parallel iteration space, achieving 5.4x and avoiding the regression seen in GPT-5's inner-loop-only approach. On the weaker end, C# achieves 3.4x with `Parallel.For` on M-tiles inside (N, K) loops, Rust achieves 2.2x using rayon's `par_chunks_mut` (writing directly to C without clone-merge overhead, but with repeated barriers), and Java manages only 1.1x with an `ExecutorService` pattern that creates synchronization barriers at every (N, K) iteration via `future.get()`.

All six implementations preserve numerical determinism through disjoint writes and fixed K-summation order. However, the justification documents share a recurring error: four of six (Java, C#, Rust, C++) incorrectly describe the M-loop as the "outermost" loop when it is actually the innermost of the three tiling loops. Additionally, the Python justification incorrectly claims that the `ProcessPoolExecutor` initializer leverages OS copy-on-write semantics to avoid serialization, when in practice `initargs` are pickled regardless of the process creation method. The Rust implementation contains a compilation-blocking bug in its sequential baseline (`_n1` vs `n1` variable naming), raising questions about how the claimed test results were produced.

These results demonstrate that Gemini 2.5 Pro generates meaningfully different parallelization architectures depending on the language, and that the choice between 2D task decomposition (one task per output block) and 1D inner-loop parallelism (repeated barriers) is the primary determinant of performance.

### 3. Shared Algorithmic Baseline

Gemini 2.5 Pro produced a structurally consistent sequential kernel across all six languages:

- **Tiling:** 3-level blocking with MB = NB = KB = 64
- **Loop order:** N-blocks -> K-blocks -> M-blocks (outer to inner)
- **B transpose:** Performed once before the tiled loops
- **Kernel:** `partialMatmul` accumulates partial products into C with alpha-scaling

---

### 4. Parallelization Strategies

#### 4.1 Two Distinct Architectures

Gemini 2.5 Pro produced two fundamentally different parallelization architectures:

**Architecture A: 2D Task Decomposition (Go, Python, C++)**
Each worker owns a complete (M, N) output block and iterates the K-dimension sequentially within its task. This produces a single synchronization point per GEMM call (or, in C++'s case, a single OpenMP parallel region).

**Architecture B: 1D Inner-Loop Parallelism (Java, C#, Rust)**
The M-dimension is parallelized within the sequential (N, K) loops. This creates a synchronization barrier at every (N, K) iteration -- 256 barriers for a 1024^3 matrix with 64-block tiles.

#### 4.2 Per-Language Details

| Language | Architecture | Parallel Dimension | Primitive | Worker Bound | Small-Input Threshold |
|----------|-------------|-------------------|-----------|-------------|----------------------|
| Go | 2D task | (M, N) tiles | WaitGroup + semaphore channel | `NumCPU()` | mBlocks * nBlocks < NumCPU |
| Python | 2D task | (M, N) tiles | `ProcessPoolExecutor` + initializer | `cpu_count()` | mBlocks * nBlocks <= cpu_count |
| C++ | 2D collapsed | (N, M) collapsed | `#pragma omp collapse(2)` | OpenMP default | m\*n > 128^2 |
| Java | 1D inner | M-tiles per (N,K) | `ExecutorService` + `future.get()` | `availableProcessors()` | None |
| C# | 1D inner | M-tiles per (N,K) | `Parallel.For` | TPL default | None |
| Rust | 1D inner | M-rows per (N,K) | rayon `par_chunks_mut` | rayon default | m < mb\*2 or n < nb\*2 |

#### 4.3 Key Design Differences from GPT-5

**Python:** Gemini uses the `ProcessPoolExecutor` initializer pattern (`_init_worker`) to pass A and Bt to workers at pool creation, reducing per-task serialization. GPT-5 serialized all data per task and capped workers at 4. This difference produces an 8.5x vs 3.0x speedup.

**C++:** Gemini uses `collapse(2)` on the N and M loops, creating a single parallel region. GPT-5 placed `parallel for` on the innermost M-loop inside (N, K) loops, creating 256 barriers. This difference produces a 5.4x speedup vs a 0.87x regression.

**Go:** Both use goroutines, but with different patterns. Gemini uses semaphore-throttled goroutine fan-out over (M, N) pairs. GPT-5 uses a channel-based worker pool over M-tiles only. Gemini achieves 9.5x vs GPT-5's 7.4x.

**Rust:** Gemini uses `par_chunks_mut` to write directly to C, avoiding GPT-5's clone-local-merge pattern. However, Gemini's approach creates barriers at every (N, K) iteration, while GPT-5 spawns threads once. GPT-5 achieves 4.5x vs Gemini's 2.2x -- the clone-merge overhead is less costly than repeated barriers.

### 5. Analysis: Why the Speedups Differ

#### 5.1 Architecture A vs B

The 2D task decomposition (Architecture A) consistently outperforms the 1D inner-loop approach (Architecture B). The key metric is synchronization frequency:

| Architecture | Barrier count (1024^3) | Best speedup | Worst speedup |
|-------------|----------------------|-------------|--------------|
| 2D task (Go, Python, C++) | 1 | 9.50x (Go) | 5.36x (C++) |
| 1D inner (Java, C#, Rust) | 256 | 3.37x (C#) | 1.10x (Java) |

With 256 barriers, each separating only 16 M-tiles of work, the overhead-to-computation ratio is unfavorable. In Java, the `future.get()` barrier and per-call thread pool creation make this overhead dominant.

#### 5.2 Python's Initializer Advantage

Gemini's Python implementation demonstrates the importance of data transfer strategy in process-based parallelism:

| Approach | Per-task data transfer | Worker count | Speedup |
|----------|----------------------|-------------|---------|
| Gemini (initializer) | Task metadata only (~56 bytes) | All CPUs | 8.53x |
| GPT-5 (per-task pickle) | Apack + Bpack + result (~24 KB) | Max 4 | 3.04x |

By passing A and Bt through the initializer, Gemini avoids serializing matrix data on every task submission. Each task tuple contains only scalar metadata `(alpha, m0, n0, m1, n1, k, KB)`.

#### 5.3 C++ collapse(2) vs Inner-Loop Parallelism

The `collapse(2)` directive merges the N and M loops into a single iteration space of 16 x 16 = 256 (N, M) pairs. OpenMP distributes these across threads in a single parallel region with one barrier. This is precisely what GPT-5's C++ implementation needed but failed to do.

### 8. Justification Inconsistencies

#### Common Pattern: M-Loop Mislabeled as "Outermost"

Four implementations (Java, C#, Rust, C++) describe the M-loop as the "outermost" loop. In all cases, the actual loop nesting is N -> K -> M (outer to inner). The M-loop is consistently the **innermost** tiling loop.

#### Per-Language Issues

**C++ (OpenMP):**
- Beta-scaling guard uses `m > 128` but justification implies it matches the GEMM guard (`m*n > 128^2`)

**Go (Goroutines):**
- Describes the pattern as a "bounded worker pool" but code uses semaphore-throttled fan-out (one goroutine per block, not reusable workers)
- Small-input threshold ignores the K dimension

**Python (ProcessPoolExecutor):**
- Claims initializer "leverages OS copy-on-write... without expensive serialization." This is incorrect: `ProcessPoolExecutor` pickles `initargs` regardless of process creation method

**Java (ExecutorService):**
- Omits the critical `future.get()` barrier between K iterations; claims there is "no merge step" when barriers occur at every (N, K) pair
- Claims "no shared writes" but the same C cells are written across K iterations (safe only due to the barrier)

**C# (Parallel.For):**
- Claims M-loop is the "outermost loop" (it is innermost)
- Beta-scaling parallelization via `Parallel.For` is undocumented in the justification

**Rust (rayon):**
- Sequential baseline contains a compilation-blocking bug (`_n1` vs `n1`)
- Threshold described as fixed "128" but is actually dynamic (`mb*2`, `nb*2`)

### 9. Conclusions

Gemini 2.5 Pro demonstrates stronger architectural awareness than GPT-5 in its parallelization decisions. The model produces two distinct architectures depending on the language, and the 2D task decomposition approach (Go, Python, C++) consistently delivers higher speedups by minimizing synchronization frequency. The most notable improvements over GPT-5 are in C++ (collapse(2) producing a 5.4x speedup vs GPT-5's regression) and Python (initializer pattern enabling 8.5x vs 3.0x).

However, Gemini's justification documents share a systematic weakness: they consistently misidentify the parallelized loop's position in the loop nest, describing the innermost M-loop as the "outermost." The Python justification also makes a factually incorrect claim about copy-on-write semantics. The Rust implementation contains a bug in the sequential baseline that would prevent compilation.

For thesis purposes, Gemini 2.5 Pro's results demonstrate that LLM-generated parallel code can achieve substantial speedups across languages when the model selects appropriate parallelization granularity. The clear correlation between 2D task decomposition and higher speedups suggests the model has some implicit understanding of synchronization costs, though this understanding is not reflected in the justification documents' explanations.
