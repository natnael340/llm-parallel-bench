# Claude Sonnet 4.5 Parallel GEMM: A Cross-Language Analysis

## Thesis-Ready Summary

Claude Sonnet 4.5 produced the most architecturally diverse set of parallel GEMM implementations among the three models tested, with three distinct parallelization patterns across six languages. Java and Rust use full 2D task decomposition with the K-loop running sequentially inside each worker, producing a single synchronization point per GEMM call. C++ and Python parallelize 2D (N, M) tile pairs but retain the K-loop as the outermost sequential loop, creating one synchronization barrier per K-block (16 for a 1024^3 matrix). Go and C# parallelize only the M-dimension within sequential (N, K) loops, creating a barrier at every (N, K) iteration (256 for 1024^3). This architectural split directly determines the performance outcomes: Java achieves the best speedup at 6.6x using a static ForkJoinPool with a single invokeAll, while Python fails entirely, unable to complete a 1024^3 multiplication within 10 hours.

The performance spread across the five successful implementations ranges from 6.6x (Java) to 2.0x (C++), driven primarily by synchronization frequency and concurrency primitive overhead. Java's architecture is the cleanest: a static ForkJoinPool (created once, not per call), full 2D decomposition over (M, N) tiles with K inside each task, and a single invokeAll synchronization. Rust achieves 4.8x with a similar 2D decomposition but pays for Arc<Mutex> lock contention when writing results back to C; its local-buffer-then-lock-write pattern avoids contention during computation but serializes the write-back phase. Go reaches 4.6x despite using 1D M-loop parallelism because goroutine scheduling overhead is low, though its 256 barriers per multiply prevent it from matching Java. C# achieves only 2.5x with the same 1D architecture using Parallel.ForEach, limited by TPL scheduling overhead at high barrier frequencies. C++ achieves 2.0x with 2D-per-K-block parallelism, held back by per-barrier OpenMP fork-join costs and in-parallel-region memory allocation. Python's failure is catastrophic: a new ProcessPoolExecutor is created for every K-block, entire input matrices (not slices) are serialized via pickle for each task, and workers return individual (row, col, value) triples rather than tile buffers.

The justification documents produced by Claude Sonnet 4.5 are notably more detailed than those of GPT-5 or Gemini 2.5 Pro, each including four to six rejected alternatives with reasoning. However, this detail introduces a recurring inconsistency pattern: three of six justifications criticize rejected alternatives for properties that the chosen implementation itself exhibits. The C++ justification rejects an alternative for "allocating Apack inside the parallel loop" while the chosen code does exactly the same. The Go justification rejects a persistent worker pool for "channel recreation overhead" while the chosen code recreates a semaphore and WaitGroup per (N, K) pair. The C# justification claims determinism derives from "fixed iteration order" when Parallel.ForEach provides no such guarantee; determinism actually comes from non-overlapping writes. These inconsistencies suggest the model generates plausible-sounding comparative reasoning without verifying it against the actual implementation.

## Detailed Reference

### 1. Scope

This chapter examines the parallel GEMM implementations generated by Claude Sonnet 4.5 across six programming languages. Each implementation parallelizes a common blocked GEMM kernel (`C := alpha * A * B + beta * C`) using language-idiomatic concurrency primitives. All measurements use a fixed **1024 x 1024 x 1024** matrix with **20 iterations and 5 repeats**.

### 3. Shared Algorithmic Baseline

Claude Sonnet 4.5 produced a structurally consistent sequential kernel across all six languages:

- **Tiling:** 3-level blocking with MB = NB = KB = 64
- **Loop order:** N-blocks -> K-blocks -> M-blocks (outer to inner)
- **B transpose:** Performed once before the tiled loops
- **Kernel:** `partialMatmul` accumulates partial products into C with alpha-scaling

### 4. Parallelization Strategies

#### 4.1 Three Distinct Architectures

Claude Sonnet 4.5 produced three fundamentally different parallelization architectures, the most diverse set among the three models tested:

**Architecture A: Full 2D Task Decomposition (Java, Rust)**
Each worker owns one or more complete (M, N) output tiles and iterates the K-dimension sequentially within its task. This produces a single synchronization point per GEMM call.

**Architecture B: 2D Per K-Block (C++, Python)**
The (N, M) tile pairs are parallelized, but the K-loop remains outermost and sequential. This creates one synchronization barrier per K-block -- 16 barriers for a 1024^3 matrix with 64-block tiles.

**Architecture C: 1D Inner-Loop Parallelism (Go, C#)**
The M-dimension is parallelized within the sequential (N, K) loops. This creates a synchronization barrier at every (N, K) iteration -- 256 barriers for a 1024^3 matrix.

#### 4.2 Per-Language Details

| Language | Architecture | Parallel Dimension | Primitive | Worker Bound | Small-Input Threshold |
|----------|-------------|-------------------|-----------|-------------|----------------------|
| Java | Full 2D | (M, N) tiles | `ForkJoinPool` + `invokeAll` | `availableProcessors()` | max(m,n) < 256 |
| Rust | Full 2D | (N, M) tiles | `thread::spawn` + `Arc<Mutex>` | `available_parallelism()` | m\*n < 16,384 |
| C++ | 2D per K-block | (N, M) pairs per K | `#pragma omp parallel for` | OpenMP default | m < 128 |
| Python | 2D per K-block | (N, M) pairs per K | `ProcessPoolExecutor` | min(cpu\_count, 8) | tiles < workers\*2 |
| Go | 1D inner | M-tiles per (N,K) | WaitGroup + semaphore | `NumCPU()` | m\*n < 10,000 |
| C# | 1D inner | M-tiles per (N,K) | `Parallel.ForEach` | `ProcessorCount` | m < 128 |

#### 4.3 Key Design Differences

**Java** is the standout implementation. It uses a static ForkJoinPool (created once as a class field, never recreated), creates all (M, N) tile tasks upfront with the K-loop inside each TileTask, and issues a single invokeAll call. This minimizes synchronization to one point and avoids pool management overhead entirely.

**Rust** uses a similar 2D decomposition but introduces a unique local-buffer-then-lock-write pattern: each worker accumulates partial products into a private local_tile buffer across all K-blocks, then acquires an Arc<Mutex> lock on C to write the final result. This eliminates contention during computation but serializes the write-back phase.

**C++** builds a vector of (N, M) tile pairs and parallelizes them with `#pragma omp parallel for schedule(static)` inside each K-block iteration. Each worker allocates its own Apack and Bpack inside the parallel region, incurring memory allocation overhead at every barrier.

**Python** suffers from three compounding design flaws: (1) a new ProcessPoolExecutor is created and destroyed for every K-block, (2) entire matrices A and Bt are pickled and sent with every task (not just the needed slices), and (3) workers return individual (row, col, value) update triples rather than tile buffers.

**Go** and **C#** share the same 1D M-loop architecture. Go uses semaphore-bounded goroutines with a new WaitGroup per (N, K) pair. C# uses Parallel.ForEach with MaxDegreeOfParallelism. Both create 256 barriers for a 1024^3 multiply.

### 5. Analysis: Why the Speedups Differ

#### 5.1 Architecture Comparison

The three architectures produce sharply different synchronization profiles:

| Architecture | Languages | Barrier count (1024^3) | Best speedup | Worst speedup |
|-------------|-----------|----------------------|-------------|--------------|
| Full 2D (K inside worker) | Java, Rust | 1 | 6.59x (Java) | 4.78x (Rust) |
| 2D per K-block | C++, Python | 16 | 1.96x (C++) | FAILED (Python) |
| 1D inner (M-loop) | Go, C# | 256 | 4.62x (Go) | 2.47x (C#) |

Architecture A consistently outperforms Architecture B despite having fewer barriers, because Architecture B's per-K-block parallelization introduces repeated thread creation and memory allocation overhead without proportional computational benefit. Go's strong showing despite Architecture C's 256 barriers reflects goroutines' extremely low per-barrier cost.

#### 5.2 Concurrency Primitive Overhead

| Primitive | Approx. per-task overhead | Barrier count (1024^3) | Cumulative overhead |
|-----------|--------------------------|----------------------|-------------------|
| `ForkJoinPool.invokeAll` | ~100 ns per task | 1 | ~26 us |
| `thread::spawn` + `Arc<Mutex>` lock | ~1 us per tile write-back | 1 | ~256 us |
| Goroutine + WaitGroup | ~50 ns | 256 | ~13 us per barrier |
| `Parallel.ForEach` | ~100 ns | 256 | ~26 us per barrier |
| OpenMP fork/join | ~1-10 us | 16 | ~16-160 us per barrier |
| `ProcessPoolExecutor` + pickle | ~1-10 ms | 16 | ~16-160 ms per barrier |

Java's ForkJoinPool achieves the best result because it combines the lightest per-task overhead with the fewest synchronization points. Rust's thread::spawn has higher fixed cost but only pays it once; the Mutex lock contention on write-back is the primary limiter. Python's ProcessPoolExecutor has overhead 4-5 orders of magnitude higher than Java's ForkJoinPool, compounded by 16 pool recreations.

#### 5.3 Python Failure Analysis

Python's failure at 1024^3 (and 0.98x at 400x300) results from three compounding overheads:

1. **Pool recreation:** A new ProcessPoolExecutor (with full process fork/teardown) is created for every K-block. At 1024^3 with KB=64, this means 16 pool cycles.
2. **Data serialization:** Each task tuple contains the entire A and Bt matrices (~1.9 MB for 400x300), not just the needed tile slices. With 245 tasks at 400x300, this transfers ~465 MB instead of ~12-24 MB.
3. **Result granularity:** Workers return individual (row, col, value) triples, requiring the main process to iterate over every non-zero update and apply it to C.

By contrast, Gemini 2.5 Pro's Python implementation uses an initializer pattern to pass matrices at pool creation (not per task), achieving 8.5x speedup on the same problem.

### 7. Correctness Properties

All six implementations preserve numerical determinism through:
1. Disjoint writes to C (spatial partitioning within each parallel region)
2. Fixed K-summation order within each worker
3. No floating-point reductions across thread boundaries

Rust adds an extra layer: each worker computes into a private local_tile buffer, then writes to C under a Mutex lock, ensuring writes are serialized and deterministic.

Python's correctness is technically preserved (it returns individual (row, col, value) updates applied in submission order), but at the cost of making parallelism effectively useless.

#### Identified Bugs

| Language | Bug | Severity |
|----------|-----|----------|
| Python | Creates new ProcessPoolExecutor per K-block instead of once per call | Critical (performance) |
| Python | Sends entire A and Bt matrices per task (~1.9 MB) instead of tile slices | Critical (performance) |
| Rust | Clones matrix A unnecessarily before wrapping in Arc (Arc alone provides shared read-only access) | Medium (memory waste) |

No correctness bugs were found in any implementation. All produce bit-exact results matching the sequential baseline.

### 8. Justification Inconsistencies

#### Recurring Pattern: Self-Contradictory Rejection Reasoning

Three of six justifications criticize rejected alternatives for properties the chosen implementation itself exhibits. This is the defining quality issue of Claude Sonnet 4.5's justification documents.

#### Per-Language Issues

**C++ (OpenMP):**
- **Critical:** Criticizes rejected alternative for "allocating Apack inside the parallel loop, causing memory allocation contention" but the chosen implementation does the same thing (lines 141-142 of gemm_parallel.cpp)
- **High:** Claims rejected alternative created "one parallel region per k-block" as a flaw, but the chosen implementation also creates one parallel region per K-block; the actual difference is per (N, K) pair vs per K-block

**Go (Goroutines):**
- **High:** Rejects Alternative 4 (persistent worker pool) for "channel close/recreate overhead" but code recreates a new semaphore and WaitGroup for every (N, K) pair -- the same pattern being criticized
- **Medium:** Underestimates goroutine count: claims "~64 tasks" but actual count is 512 goroutines for 512^3 (8 m-blocks x 64 (N,K) pairs)

**Python (ProcessPoolExecutor):**
- **Critical:** Claims per-task data transfer is "50-100 KB" when actual transfer is ~1.9 MB per task (entire A and Bt matrices, not slices)
- **High:** Parallel version uses K-loop as outermost, differing from sequential version's (N, K, M) nesting -- contradicts claim of "identical accumulation order"

**Java (ForkJoinPool):**
- **High:** Claims "Null/empty matrices: validation throws exceptions" but C=null is explicitly supported and creates a zero matrix
- **Medium:** Describes workers as using "private buffers" when they write to non-overlapping regions of the shared C matrix

**C# (Parallel.ForEach):**
- **Critical:** Claims "fixed iteration order" ensures determinism, but Parallel.ForEach provides no ordering guarantee. Determinism actually derives from non-overlapping writes
- **High:** Claims "Apack and Bpack buffers are read-only during the parallel section" but each worker creates its own Apack inside the parallel region
- **Medium:** Describes m0 as "the innermost loop" when it is actually the 3rd of 6 nesting levels

**Rust (thread::spawn):**
- **High:** Clones matrix A before wrapping in Arc, adding unnecessary memory overhead not mentioned in justification
- **Medium:** Claims 64x64x64 matrices use parallel execution, but m*n=4096 falls below the sequential threshold of 16,384
- **Medium:** Lock hold duration during nested write loops is longer than the justification implies

### 9. Conclusions

Claude Sonnet 4.5 demonstrates the most architectural diversity among the three models tested, producing three distinct parallelization patterns across six languages. This diversity is both a strength and a weakness: the model selects the strongest available architecture (full 2D with K inside worker) for Java and Rust, but applies weaker patterns to the remaining languages. The result is a wider performance spread (6.6x to FAILED) than either GPT-5 (7.4x to 0.87x) or Gemini 2.5 Pro (9.5x to 1.1x).

Java is Claude Sonnet 4.5's best implementation and the best single-language result across all three models except for Gemini's Go (9.5x) and C++ (5.4x). The static ForkJoinPool pattern represents genuine architectural awareness: creating the pool once, distributing all tiles in a single invokeAll, and keeping K inside each task. However, the model failed to apply this same pattern to other languages where it would have been equally effective.

Python is Claude Sonnet 4.5's worst implementation and the only complete failure across all 18 implementations (3 models x 6 languages). The combination of per-K-block pool recreation, per-task full-matrix serialization, and individual-cell result granularity creates overhead that scales superlinearly with problem size.

The justification documents are the most detailed of the three models but also the least self-consistent. The recurring pattern of criticizing rejected alternatives for properties the chosen implementation shares suggests the model generates comparative reasoning from general knowledge rather than from analysis of the specific code it produced. This is a distinctive weakness: GPT-5's justifications are sparser but more accurate, and Gemini's share a different systematic error (loop-level mislabeling) that at least does not contradict the code's actual behavior.
