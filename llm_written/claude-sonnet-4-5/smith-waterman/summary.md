Two parallelization strategies appear across the Claude Sonnet 4.5 Smith-Waterman implementations: **wavefront parallelization** of the dominant matrix-construction phase and **parallel reduction** over the post-construction maximum-score search. These strategies are not mutually exclusive. C# and Go apply both, parallelizing the matrix fill via wavefront and the max-finding via parallel reduction. Java parallelizes only the matrix fill while keeping max-finding sequential. C++, Python, and Rust take the conservative approach of keeping matrix construction entirely sequential and parallelizing only the max-finding scan. Whether an implementation attempts to parallelize the matrix-fill phase, and at what synchronization granularity, is the most consequential architectural variable in the entire set and almost entirely determines the performance outcome.

The wavefront strategy targets the correct bottleneck. Matrix construction constitutes roughly ninety-five percent of Smith-Waterman runtime and exhibits a well-known anti-diagonal independence property: cells sharing the same value of `i + j` depend only on cells from earlier anti-diagonals, so all cells on a given anti-diagonal can be computed concurrently. The three wavefront implementations exploit this property but differ critically in granularity. C# issues one `Parallel.For` per anti-diagonal, creating approximately `n + m` synchronization barriers for an n-by-m matrix, each involving TPL task scheduling for very little per-cell work. Java similarly iterates over individual anti-diagonals but uses a static `ForkJoinPool` and chunks cells into groups of at least 64 before submitting tasks, reducing per-task overhead while still incurring one barrier per anti-diagonal. Go takes a fundamentally different approach: it divides the matrix into **256-by-256 blocks** and processes block anti-diagonals, so each parallel task fills 65,536 cells sequentially within its block before any synchronization occurs. This coarsening reduces the number of synchronization barriers from thousands to tens while preserving far more useful work per barrier.

The conservative strategy (C++, Python, Rust) recognizes that the tight three-cell dependency structure makes matrix-fill parallelization difficult and instead targets only the post-construction scan for the global maximum score. This scan is embarrassingly parallel: each row can be scanned independently and a deterministic reduction produces the global maximum. All three follow the same pattern of partitioning rows among workers, finding thread-local maxima, and merging in a fixed order --- C++ via OpenMP with static scheduling and lexicographic tie-breaking, Rust via Rayon's `par_iter` with a `reduce` combinator, and Python via `ProcessPoolExecutor` with explicit row-chunk serialization. All three justifications correctly invoke Amdahl's law to explain that parallelizing approximately five percent of the total work can yield at most roughly 1.05x theoretical speedup.

The standardized benchmark results reveal a stark divide:

| Lang   | Strategy              | Parallel (ms) | Sequential (ms) | Speedup   |
| ------ | --------------------- | ------------- | --------------- | --------- |
| Go     | Block wavefront + max | 641.68        | 3628.23         | **5.66x** |
| Rust   | Max-finding only      | 919.76        | 1079.18         | **1.17x** |
| C++    | Max-finding only      | 1436.43       | 1416.93         | ~1.00x    |
| C#     | Cell wavefront + max  | 3969.22       | 3108.03         | 0.78x     |
| Java   | Cell wavefront        | 11152.40      | 2004.84         | 0.18x     |
| Python | Max-finding only      | _killed_      | 216645.40       | N/A       |

Go's block wavefront is the only implementation that delivers unambiguous speedup on the matrix-fill phase. Some caution is warranted: the LLM's own `perf.txt` reports a more conservative 1.39x on 2000-by-2000 sequences, and the sequential baseline timing may reflect the original test harness rather than a perfectly controlled comparison --- but even at the lower figure, the result is strong. Rust's 1.17x is consistent with the Amdahl's law ceiling for parallelizing only max-finding. C++ at parity is similarly explained. C#'s 0.78x reflects the catastrophic overhead of per-anti-diagonal `Parallel.For` invocations in the TPL. Java's 0.18x (a 5.56x slowdown) shows that submitting chunked tasks to the `ForkJoinPool` with barrier synchronization across thousands of anti-diagonals far exceeds the parallelism benefit at this scale. Python was killed during benchmarking; the LLM's own measurements show consistent 0.14x--0.36x slowdowns from `ProcessPoolExecutor` process-spawning overhead and matrix pickling costs.

The performance divergence within the wavefront group is explained almost entirely by synchronization granularity and task-creation policy. C# and Java both synchronize once per anti-diagonal, creating thousands of barriers for typical inputs with task scheduling overhead that dwarfs the few arithmetic operations per cell. Java's chunking of 64+ cells per task reduces per-task overhead but does not eliminate the one-barrier-per-anti-diagonal problem. Go's block wavefront reduces the barrier count by a factor proportional to the block size, so a 2000-by-2000 matrix requires roughly fifteen block anti-diagonals rather than four thousand cell anti-diagonals. Go's goroutines also have extremely low creation overhead (typically sub-microsecond) compared to C#'s TPL tasks or Java's `ForkJoinPool` submissions, further favoring the Go implementation even before block-level amortization. Within the conservative group, Rayon and OpenMP add negligible overhead, while Python's `ProcessPoolExecutor` incurs the heaviest penalty due to process spawning and data serialization costs inherent to circumventing the GIL.

The justifications are **structurally templated** across all six languages, sharing identical section headings, ASCII diagram conventions, glossary definitions, and an eight-section format ("What Changed and Why," "How We Made It Parallel," "Why the Answer Is Always the Same," etc.). Despite this, the strategy-level content varies appropriately: wavefront implementations describe anti-diagonal or block anti-diagonal processing, while conservative implementations describe parallel max-finding with sequential matrix fill. Each justification includes rejected alternatives with concrete explanations, and these are generally consistent with the code and data. Notably, the C++ justification reports that anti-diagonal wavefront caused a 6x slowdown, the Go justification documents a refinement from 0.21x (fine-grained wavefront) to 1.39x (block wavefront), and the Rust justification cites a 14--100x slowdown from wavefront. These cross-language rejections are corroborated by the C# and Java results, which demonstrate exactly those predicted slowdown patterns.

The most significant **credibility issue** lies with Java. The justification claims a 2.86x speedup on a 1000-by-1200 matrix (1.2M cells), but the parallel threshold is set at 2M cells, meaning the 1000-by-1200 test falls below threshold and would have executed the sequential fallback path. The reported "parallel" speedup may therefore reflect the sequential code path rather than actual parallel execution. Meanwhile, the standardized benchmark on a larger input that exceeds the threshold shows a 5.56x slowdown --- the most consequential mismatch between claimed and observed performance in the entire set. By contrast, the C# justification is commendably transparent about its slowdown, the Python justification explicitly acknowledges the overhead, and the C++ and Rust justifications are the most credible overall: their claims align with benchmarks and their Amdahl's law reasoning is sound.

All six implementations are **correct** with respect to the core DP recurrence. The wavefront implementations correctly identify and respect the anti-diagonal independence property; the sequential implementations preserve standard row-major dependency ordering. No data races, deadlocks, or incorrect cell computations were identified. Traceback is sequential in all six, which is appropriate. Two minor determinism concerns exist: in C#, thread-local maxima are appended to a shared list under lock in arrival order rather than worker-index order, making tie-breaking among equal scores non-deterministic; in Rust, the Rayon `reduce` combinator does not guarantee a fixed traversal order, creating the same issue. These are unlikely to manifest with random biological sequences where the global maximum is typically unique, but they represent gaps in the claimed determinism guarantees that no justification acknowledges.

The single most important determinant of success is **synchronization granularity relative to per-task work**. Go succeeds because it synchronizes once per block anti-diagonal with 65,536 cells of work per block, achieving a computation-to-synchronization ratio orders of magnitude higher than C# and Java, which synchronize once per cell anti-diagonal with only hundreds of cells per barrier. The conservative implementations avoid this problem entirely by not parallelizing the matrix fill, but accept the Amdahl's law ceiling of negligible speedup. The evidence strongly suggests that for Smith-Waterman on multi-core CPUs at typical bioinformatics scales, the only viable parallelization strategy is coarse-grained block wavefront with block sizes large enough to amortize synchronization overhead, and that fine-grained per-anti-diagonal parallelism is counterproductive regardless of the language or concurrency framework used.
